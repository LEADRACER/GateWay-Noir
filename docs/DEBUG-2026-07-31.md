# Noir:GateWay — Serious Debug Report (AGT + DET perspectives)

Date: 2026-07-31
Scope: server, API endpoints, workflows. n8n / WAHA explicitly excluded (user self-setup).
Targets tested: localhost:3000 (next dev) + https://gate-way-noir.vercel.app (prod) + hosted Supabase bovsdzvkhtcilsvkayec.supabase.co

## Summary

All criticals are in AUTH + DATA ACCESS, not in feature logic. The role-gate pattern
(getCurrentUser → role check) works correctly everywhere it is applied — every BUREAU-
only route returned 403 for anonymous callers. The failures are endpoints/actions that
SKIP the gate, and one architectural flaw: RLS disabled + public anon key = full DB access.

## Findings

### CRITICAL

1. RLS is OFF on hosted Supabase — full DB compromise via public anon key
   - Proof: GET /rest/v1/User?select=badgeCode,displayName,role,passwordHash,phone&limit=5
     with the NEXT_PUBLIC anon key returned real users incl. bcrypt passwordHash.
   - Proof: POST /rest/v1/Comment with anon key inserted a row directly.
   - The anon key is in the browser bundle (NEXT_PUBLIC) → anyone with devtools can dump
     or write every table: users, badge codes, phones, password hashes (offline crackable),
     topics, comments, elevation requests, agent tasks.
   - Root cause: scripts/schema.sql has RLS commented out; tables created without
     `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`.
   - Fix: enable RLS on all tables + policies (public read on Topic/Category/Comment/Vote;
     self-scoped reads on User; BUREAU-only writes), OR switch server-side client to
     service_role key and keep anon locked down. Also: stop selecting passwordHash in the
     server client (it is returned to the server-side code that runs as the app, but via
     anon key today it is exposed to the world).

2. Session cookie = the badge code itself (no signature, no server-side store)
   - noirgateway_session value is literally `badgeCode` (session-cookie.ts).
   - getCurrentUser() trusts it after a DB lookup by badgeCode.
   - Proof: `Cookie: noirgateway_session=BRU-DTWZ` → full BUREAU access (elevation pending,
     agent discussions, admin check all 200). `AGT-WR8C` → agent access. `DET-VUQ3` → 403
     on agent routes (role gates hold).
   - Badge codes are 4 chars from 32-char alphabet ≈ 1,048,576 combos, no rate limiting
     on lookup paths → brute-forceable.
   - Fix: server-side session store (DB or signed JWT with secret), opaque random token,
     expiry + rotation; never the raw badge code.

3. /api/badge/claim = account takeover for any unclaimed badge
   - Claim sets passwordHash when the badge has none (claim/route.ts).
   - All admin-created users (createAgentUser/createBureauUser) and all self-generated
     badges are created with passwordHash = NULL → every one of them is claimable.
   - Combined with the /api/badge/name 404-vs-200 oracle, an attacker can enumerate
     existing codes (BRU-XXXX, AGT-XXXX, DET-XXXX — 1M each) and take over the first
     unclaimed one, including BUREAU accounts.
   - Proof (local): generated DET-MMS4 via generate → DB showed passwordHash NULL,
     linkedIds=[anon]. Claim was not re-run after the user blocked further mutations,
     but code path is unambiguous.
   - Fix: only allow claim when passwordHash IS NULL **and** badge is a DETECTIVE badge
     owned by the caller's flow (e.g. claim link delivered out-of-band), require the
     badge code to be a high-entropy one-time token for admin-created accounts, or make
     admin-created users start with a temporary password.

### HIGH

4. /api/cron/timeout-topics is unauthenticated and unscheduled
   - Guard: `if (process.env.CRON_SECRET && token !== process.env.CRON_SECRET)` — CRON_SECRET
     is unset in .env, .env.local, .env.prod → guard is a no-op in both local and prod.
   - Proof (prod): POST with `Authorization: Bearer wrong-secret-123` → HTTP 200
     {"autoConcluded":0,"autoDeleted":0,"errors":[]} — it EXECUTED.
   - Behaviour: auto-concludes ACTIVE topics past endsAt with verdict "UNSOLVED" and
     auto-DELETES CONCLUDED topics older than 7 days (topics + comments + votes).
   - Nothing schedules it: no vercel.json cron, no external trigger known.
   - Live side-effect during this debug: concluded expired "Moon landing" topic and purged
     older CONCLUDED seed topics. Data loss confirmed.
   - Fix: set CRON_SECRET (add to Vercel env + .env.prod), verify bearer before running,
     add vercel.json cron schedule (or keep external n8n trigger — your call), and add a
     dry-run flag / confirmation step before the delete phase.

5. /api/badge/name and /api/badge/phone — unauthenticated user profile writes
   - Any caller knowing a badgeCode can rename that user (name route) or overwrite their
     phone + null their whatsappId (phone route). The name route also acts as a badge-code
     existence oracle (200 vs 404 "Badge not found").
   - Fix: require session (getCurrentUser) and check the caller owns the badge (linkedIds
     contains the caller's anonymousId or caller badgeCode matches).

### MEDIUM

6. /api/elevation/request — no auth, client-supplied userId, no rate limit
   - Proof: anonymous POST with a real DETECTIVE userId → HTTP 200 (request created).
   - Any anonymous visitor can spam elevation requests for any DETECTIVE; admin queue
     floods; duplicate guard only prevents exact repeats.
   - Fix: bind userId to the caller's own account (getCurrentUser → user.id), add
     rate limit + cooldown between requests.

7. Server actions without auth (invocable via action endpoints):
   - createAgentUser / createBureauUser: role check only applies when creating BUREAU.
     Anyone can mint AGENT (and DETECTIVE) users. Combined with finding #3 = free agent
     account.
   - getAllUsers / getUsersByRole / updateTaskStatus: no auth. Any visitor can enumerate
     every user or flip any task to COMPLETED (I saw this path in task-actions.ts).
   - Fix: getCurrentUser() + role check at the top of each action; restrict user
     enumeration to BUREAU; restrict task updates to the assigned agent or BUREAU.

### LOW

8. Fake-success responses: /api/agent/discussions POST returns 201 even when the insert
   fails (error not checked — confirmed: my DBG test insert failed silently, 201 returned,
   no row created). Same pattern in /api/agent/discussions/[id]/messages POST and
   /api/elevation/request (no insert error check).
9. Verdict "UNSOLVED" from timeout cron is not in the UI palette (BUSTED/TRUE/INCONCLUSIVE)
   — auto-concluded topics render without verdict color.
10. /api/admin/check GET accepts `noirgateway_admin=authenticated` cookie blindly
    (client-spoofable; real gates are badge-based so impact is limited to the check UX).
11. createTopic stores `createdBy` from client-supplied adminId form field (BUREAU-gated,
    low risk; should use caller.id instead).
12. Badge generate links anonymousId, but /api/badge/status on that anon returned
    hasBadge:false (reveal/status flow inconsistent with generate/claim flow).

## Recommended fix order

1. RLS: enable on all tables + policies (or service_role for server) — stops the anon-key dump
2. Session: opaque signed token or DB session table; never raw badgeCode
3. Claim: gate on passwordHash IS NULL + high-entropy codes for admin-created users
4. CRON_SECRET into .env.prod + Vercel; schedule via vercel.json cron
5. Auth on name/phone routes + elevation/request caller binding
6. Auth on the four unguarded server actions
7. Error-check inserts; verdict palette for UNSOLVED
